# SheltreSim — Working Design Notes (for Claude, cross-session reference)

> Purpose of this file: persistent context so any future session (or me, resumed) can pick up this project without re-deriving decisions. Update it as things change — treat it as the source of truth over whatever is in my head from a prior conversation.

## Elevator pitch

First-person bunker-builder + survival game. Small scale, Fallout-inspired but far smaller in scope. Player builds out a bunker before an apocalypse event, then survives inside it and makes supply runs into one outdoor area.

## Core loop (MVP target)

1. **Build phase** — player constructs/expands a bunker (multiple rooms) before the apocalypse trigger.
2. **Apocalypse event** — scripted trigger, forces player into the bunker.
3. **Survive phase** — manage hunger/thirst/health inside the bunker over time.
4. **Scavenge phase** — venture into one outdoor map to gather resources, encounter simple threats, return before survival stats run out.
5. Loop 3–4 repeats; crafting turns raw resources into usable items/upgrades.

Scope is explicitly: **bunker with multiple rooms + one outdoor map + basic crafting + simple enemies/hazards.** Not an open world, not procedural generation, not multiplayer.

## Assumptions not yet confirmed with user (flag these, don't silently lock in)

- No multiplayer/co-op — single player only.
- No plan (yet) to publish on Steam — treat as a personal/hobby project unless stated otherwise. This affects how much polish vs. working-prototype quality matters.
- **Architecture decision made autonomously (M4):** the outdoor map is NOT a separate Unity scene — it's built as an extension of the same `M1_BunkerShell.unity` scene, directly beyond the bunker's doorway. Reasoning: a real scene-transition architecture needs persistent state across scene loads (`DontDestroyOnLoad`, or a save/reload-on-transition scheme) which is a meaningfully bigger, riskier piece of plumbing to get right with no Unity Editor available to test it. A single scene sidesteps that entirely — nothing unloads, so the player/stats/inventory/placed pieces just keep existing. Revisit this if the outdoor area grows large enough that having it all loaded at once becomes a real performance problem (unlikely at this project's scale).

## Milestones (confirmed order — M1 → M7, no reordering)

Given the "longer session per milestone" working style, each milestone should be a self-contained, testable chunk:

1. **M1 — Player & bunker shell**: FPS controller, a hand-built starting bunker room (no building system yet), basic interact raycast. Goal: can walk around a static bunker.
2. **M2 — Building system**: grid placement, snapping, room/wall pieces, resource cost gating (resources can be stubbed/free for now). Goal: can expand the bunker.
3. **M3 — Survival stats + save/load**: hunger/thirst/health ticking, HUD bars, save/load of player + bunker state. Goal: can leave and resume a session with state intact.
4. **M4 — Outdoor map + resource gathering**: one hand-built outdoor scene, interactable resource nodes, inventory. Goal: can scavenge and bring resources back.
5. **M5 — Crafting**: basic recipes turning raw resources into usable items/building materials.
6. **M6 — Enemies**: simple raider/mutant AI in the outdoor map — detection, movement, attack.
7. **M7 — Apocalypse trigger + full loop glue**: scripted intro event, wiring build-phase → apocalypse → survive/scavenge loop together.

- 2026-11-07: **Final QC review pass before the first public push.** Skeptical read of every uncommitted change (M8 + the bug-fix batch), re-verified by the usual headless batch method. Five findings, four of them corrections to claims the previous session made.
  1. **The flagged melee SphereCast "self-hit" risk does not exist — the diagnosis was backwards.** The M8 entry above worried that `Physics.SphereCast` originating at the CameraPivot (Y=1.6, inside the player's own CharacterController capsule — radius 0.35, spanning Y 0–1.8) would self-hit the player at distance 0 and never reach an enemy. Unity's own docs for 6000.6 say the opposite, explicitly: *"SphereCast will not detect colliders for which the sphere overlaps the collider."* The single-hit overload **silently skips** colliders it starts inside, so the player's own body was never a problem and melee was not broken this way. No origin offset was applied — it would have fixed nothing and risked starting the sweep on the far side of a wall when backed against one.
  2. **That same rule does cause a real bug, in the opposite direction — fixed.** Because initially-overlapping colliders are skipped, an enemy *too close* is skipped as well. The numbers make this reachable, not theoretical: raider capsules are radius 0.5 and the player's controller is radius 0.35, so walking into a raider closes the centre-to-centre gap to ~0.85m, inside this cast's 0.5 (sphere) + 0.5 (capsule) = 1.0m overlap threshold. Result: you could not hit a raider pressed right up against you — precisely when you'd swing. `MeleeAttacker` now uses `Physics.SphereCastAll` (which *does* return those zero-distance overlap hits), discards any collider whose `transform.root` is the player's own rig, and takes the nearest of what remains. Taking the nearest hit of any kind, rather than the nearest enemy, deliberately preserves the old behaviour where a wall between you and a raider blocks the swing. Swing radius is now a named `attackRadius` field instead of a magic `0.5f`.
  3. **The "duplicate UI canvas" root cause is not reproducible in batch mode — the guards are right, but for a narrower reason than stated.** The M8 entry asserts that `AddComponent` from an editor tool runs `Awake` immediately at edit time, saving a dead canvas into the scene. Checked the actual scene YAML: neither the freshly batch-built scene nor the previously committed one contains `HUD_Canvas`, `PauseCanvas`, `Inventory_Canvas`, or an `EventSystem` object. So under `-batchmode -nographics`, edit-time `Awake` does **not** fire on `AddComponent`, and no stale canvas is ever written to the scene file. The `DestroyImmediate` guards in `SurvivalHUD`/`InventoryUI`/`PauseMenu` are therefore no-ops on a batch-built scene; they only do real work when the Tools-menu items are run by hand in the interactive Editor, which is almost certainly how the reporting playtester produced the frozen bars. Keeping the guards (they're correct and cost nothing), but a future session should know that **batch-mode verification cannot prove that particular fix works** — it has to be checked in the real Editor.
  4. `PauseMenu.EnsureEventSystem()` — **confirmed present, correct, and complete** after the rogue-fork clobbering. It's the only thing in the project that creates an `EventSystem` + `InputSystemUIInputModule`; `M8MenusSetup` correctly does not duplicate it. Since the batch-built scene contains no `EventSystem` object (see 3), this runtime-`Awake` creation is the *only* thing that makes the Resume/Quit buttons clickable at all — removing it, as the rogue fork did, would have silently broken the pause menu with zero compile errors and a clean batch run. Also verified `FirstPersonController` only touches `Cursor.lockState` in `OnEnable`/`OnDisable`, not per-frame, so the pause menu's cursor unlock isn't fought over frame-by-frame.

     - `EnemyAI.Start()` set `health = maxHealth` *after* the `FirstPersonController` lookup's early return. `health` is a serialized public field saved into the scene as 0 (Start never runs at edit time), so on the error path an enemy would sit at 0 HP and die to the first swing that touched it. Initialisation moved above the early return.

The (correct) ghost-pivot offset from this batch leaves the ghost's bottom face perfectly coplanar with the surface it rests on, and an exact-tangency overlap test is a floating-point coin flip — a false positive would have resurrected the "everything's always red" bug the offset was added to fix.   - **Method note first, because it is reusable: Unity's physics-query semantics were settled empirically, not from prose.** A throwaway `Assets/Editor/_TempPhysicsProbe.cs` built a scene matching the real player/enemy/wall dimensions and logged actual `SphereCastAll` / `SphereCast` / `Raycast` / `CheckBox` results via the normal `-batchmode -executeMethod` path, then was deleted.     - `SphereCastAll` returns already-overlapping colliders with `distance = 0` **and `point = (0,0,0)`** — no contact geometry at all.
    - the single-hit `SphereCast` returns **nothing whatsoever** in that same setup — it drops every overlapping collider, including the enemy at 0.85m.
    - the player's own body collider **is** returned (at distance 0) when the origin is inside it, so `MeleeAttacker`'s root-filter is load-bearing, not belt-and-braces. (A `CharacterController` specifically never appeared in Edit-mode results — it seems not to create a PhysX actor outside Play Mode — so a plain `CapsuleCollider` was used as the stand-in for that check.)
    - a wall genuinely *between* player and enemy reports a real distance (0.4 for a wall at 1.0m, vs 0.805 for the raider behind it), so distance ordering does work for things actually swept into.
    - `Physics.CheckBox` with exactly-tangent half-extents returns **True** (overlapping), and **False** with the 1cm skin. The first pass's skin fix was not just prudent, it was required — without it the ghost would have been red deterministically, not occasionally.
  1. **The melee sweep was broken by the previous QC pass's own fix, in a way neither pass could have seen without measuring. Fixed.** That pass correctly switched `MeleeAttacker` from `SphereCast` to `SphereCastAll` so a point-blank raider isn't skipped, then fed every returned hit into a single "nearest wins" comparison. But overlap hits come back at `distance = 0`, so **any collider merely touching the 0.5m sphere beat everything else and swallowed the swing** — and the player can stand within 0.35m of a surface, so that is every wall, crate, rubble prop and bit of starting furniture the player happened to be standing *beside*, not facing. Net effect: swinging anywhere near bunker geometry logged "Swing missed - nothing to hit" no matter what was in front of you, and point-blank hits were a coin flip on array order (two hits both at distance 0, strict `<` keeps whichever came first). `FindSwingTarget` now treats the two populations as the different things they are: distance-0 hits mean only "this is touching me" and are consulted **solely** to find a point-blank enemy (overlapping scenery is ignored — scenery you are standing against is not between you and anything); distance>0 hits keep the old nearest-wins-and-scenery-blocks logic, which the probe confirms still blocks a wall genuinely in the way.
  2. **Death could not happen during the Building phase. Fixed.** `SurvivalStats.Update()` early-returned on `decayPaused`, and the `health <= 0 -> Die()` check sat *below* that gate. But `decayPaused` only means "stats don't tick down by themselves" — `EnemyAI.TryAttack()` writes `playerStats.health` directly and has no notion of game phase, so raiders outside the bunker damage you before the apocalypse button is ever pressed. A player ground to 0 HP pre-apocalypse stayed alive, unfrozen and un-damageable-further, and then dropped dead a frame after triggering the apocalypse. Same ordering mistake as the `EnemyAI.Start()` one the first pass found — a check placed after an early return that it needs to precede. Death is now evaluated above the `decayPaused` gate.
  3. **Loading a save after dying left the game permanently unrecoverable. Fixed.** `SurvivalStats.Die()` disables `FirstPersonController` and `PlayerInteractor`; `SaveManager`'s load path wrote `stats.health` as a plain field assignment and nothing ever cleared `IsDead` or re-enabled those components. F9 after death therefore restored a full health bar to a player who could not move, look or interact, forever. Load now goes through a new `SurvivalStats.RestoreVitals()` which clamps the three vitals and undoes `Die()` when the restored health is above zero.
     - That fix exposed a second, latent one: **`FirstPersonController.OnDisable()` was calling `input.Dispose()`**, so the component could not survive a disable/re-enable cycle — `OnEnable` would have tried to `Enable()` a disposed `InputActionMap`. Disposal moved to `OnDestroy` (still runs on scene unload and quit, so nothing leaks). The same `Dispose()`-in-`OnDisable` pattern is still present in `BuildModeController`, `MeleeAttacker`, `SaveManager`, `InventoryUI` and `PauseMenu` — left alone deliberately, because nothing in the project disables any of those, but **it is a trap for anyone who later adds code that does.**
  4. **One Escape press could both exit build mode and open the pause menu. Fixed.** `BuildModeController` (CancelBuild) and `PauseMenu` both bind `<Keyboard>/escape` on separate, independently-enabled action maps. `PauseMenu` guarded itself with `if (buildModeController.IsBuildModeActive) return;` — which only works if its callback runs *before* build mode's. The Input System gives no ordering guarantee between two maps bound to the same control, and registration order here follows scene component order, so the guard was a coin flip: if CancelBuild ran first, `IsBuildModeActive` was already false when PauseMenu looked at it. Added `BuildModeController.ConsumedCancelThisFrame` (a `Time.frameCount` stamp set when Escape actually cancels); PauseMenu checks both, making the hand-off order-independent.
  5. **Three ways the pause menu wasn't actually paused. Fixed.** `Time.timeScale = 0` stops `Time.deltaTime`, nothing else — `Update` and input callbacks keep running, and this project has no notion of UI input consuming gameplay input (every map is hand-built and always listening). So: (a) `FirstPersonController.HandleLook()` is driven by raw mouse delta, *not* multiplied by `deltaTime`, so the view spun around behind the pause panel as the player moved the mouse toward the Resume button; (b) the left-click that presses Resume also fired `MeleeAttacker`, swinging at (and damaging) whatever was in front of you, with the swing coroutine then frozen mid-arc until resume; (c) **B** still entered build mode from behind the panel, floating a ghost over it and turning the next click into a piece placement. Guards added in all three places. Build mode and pause are now genuinely mutually exclusive in both directions.
  6. **Two smaller ones.** `SaveManager`'s load wrote `transform.position` on a live `CharacterController` — a teleport the controller can stomp with its own cached position; it now disables the controller around the write, the standard idiom. And `PauseMenu`'s canvas shared `sortingOrder = 0` with the two other independently-built overlay canvases (`SurvivalHUD`, `InventoryUI`), leaving the modal's draw order against the centre-screen inventory panel to chance — pinned to 100.
